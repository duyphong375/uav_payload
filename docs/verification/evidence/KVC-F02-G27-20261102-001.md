phép đo AWB**. Muốn xác nhận phải đọc thanh ghi AWB qua SCCB hoặc tắt AWB rồi

#### Vì sao KHÔNG phải jitter USB

Lập luận trong F-06 cũ (P3) là: USB CH340 gom gói nên mốc `[ 1795.2]` do PC in
có thể trễ, và độ trễ đó đủ để tạo tỉ lệ 0,82 sai. **Đọc source bác bỏ điều này:**

```c
/* main.c:95-106 */
static void delay_ms(uint32_t ms) {
    while (ms--) {
        SysTick->LOAD = (12000000UL / 1000UL) - 1UL;
        /* ... chờ COUNTFLAG ... */
        kvc_timebase_add_ms(1U);      // ← chỉ tăng khi ai đó GỌI delay_ms
    }
}

/* main.c:133-135 */
static uint32_t kvc_millis(void) { return kvc_timebase_ms(); }
```

`kvc_millis()` **không đọc timer**. Nó trả về một biến đếm phần mềm, chỉ tăng
khi `delay_ms()` hoặc `kvc_usound_delay_us()` được gọi. Thời gian CPU dùng để
chạy code thật (poll cảm biến, tính georef, ghi log, chờ SPI LoRa) **không được
đếm**.

Đã kiểm `kvc_timebase_add_us` xuất hiện ở đâu:

| Nơi | Có gọi? |
| :--- | :--- |
| `firmware/mcu_payload/src/kvc_timebase.c:25` | định nghĩa |
| `firmware/mcu_payload/tests/test_kvc_timebase.c` | 5 lần — **chỉ trong test** |
| Firmware production | **0 lần** |

Vậy cả hai đường cộng dồn đều phụ thuộc việc code có đi qua `delay_*` hay
không. Đây là **thiếu hụt có hệ thống trong thiết kế timebase**, không phải
nhiễu đo.

**Kiểm chéo độc lập — chứng minh jitter USB không giải thích được:**

| Bằng chứng | Suy ra |
| :--- | :--- |
| Jitter USB chỉ làm **trễ** mốc, tức làm wall-clock **dài hơn** thực | Nếu chỉ do jitter, wall phải **lớn hơn** MCU — đúng chiều |
| Nhưng jitter không thể tạo **tỉ lệ ổn định 0,82** trên **1.456 mẫu** | Jitter là ngẫu nhiên, không tạo được bias hệ thống |
| `min 0,14 s / max 3,93 s` giữa hai dòng liên tiếp | Đúng là có jitter, nhưng nó **dao động quanh** giá trị trung bình, không dồn một chiều |
| Drift **thay đổi theo tải** (0,740 → 0,856) | Khớp giả thuyết "thời gian chạy code không được đếm"; jitter USB không biết tải CPU |

Nói cách khác: jitter USB có thật và làm **nhiễu** phép đo, nhưng **không thể**
tạo sai lệch hệ thống 18 % trên 1.456 mẫu. Nguyên nhân gốc là `kvc_millis()`
không đếm thời gian chạy code.

**Điều vẫn chưa loại trừ được (giữ trung thực):** chưa tách được bao nhiêu phần
trăm trong 18,3 % là do IHRC 12 MHz ±2 % (ghi trong comment `main.c:123`) và bao
nhiêu là do thời gian không được đếm. Muốn tách phải so `[M3] t` với
`frame_timestamp` của FPGA (hiện không in ra) hoặc dùng 1PPS GNSS. **Nhưng dù
chia thế nào, trần sai số của IHRC là ±2 %, không đủ giải thích 18,3 %.**

**Ảnh hưởng:**

| Đối tượng | Ảnh hưởng |
| :--- | :--- |
| `timestamp_ms` IF-02 | **SAI ~18 %** — GCS hiển thị lệch, expiry/TDM sai |
| Ngưỡng staleness GNSS (3000 ms) | Thực tế còn ~2.450 ms → Yaw hết hạn sớm hơn |
| `KVC_FPGA_TIMEOUT_MS` (2000 ms) | Thực tế còn ~1.634 ms → dễ báo mất frame giả |
| Chu kỳ telemetry danh nghĩa 1 Hz | Thực tế **0,82 Hz** |
| `late_max = 0`, `ovr = 0` | **Không đáng tin** — đo bằng chính đồng hồ bị lỗi |

**Vì sao `late_max = 0` vẫn báo:** vòng chờ so `kvc_millis()` với
`cycle_start_ms`, cả hai cùng từ đồng hồ phần mềm. Đồng hồ chậm bao nhiêu thì
cả hai chậm bấy nhiêu, hiệu số luôn ~1000 ms. **Tiêu chí "chu kỳ 1 Hz" không
kiểm được gì khi dùng đồng hồ bị lỗi làm chuẩn.**

**Vì sao chỉ lộ ra bây giờ:** mọi phép đo trước đều đọc `t=` do MCU tự in. Chỉ
khi có soak 30 phút với **mốc wall-clock độc lập** mới so được hai đồng hồ.

**Chưa sửa.** Đây là task `KVC-MCU-TB-001` (plan B4) — phải đổi nguồn thời gian
sang timer phần cứng free-running, không phải sửa một dòng.
